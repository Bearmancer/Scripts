## 2. Root Cause Analysis: Test Failures

### Primary Failure Pattern: "Pending Model Changes" (53 failures)

**Error Message**:
```
System.InvalidOperationException: An error was generated for warning 
'Microsoft.EntityFrameworkCore.Migrations.PendingModelChangesWarning': 
The model for context 'ScriptsDbContext' has pending changes. 
Add a new migration before updating the database.
```

**Root Cause**: The compiled model (`ScriptsDbContextModel.Instance`) is out of sync with the runtime entity configurations. When `Database.MigrateAsync()` is called in the test fixture, EF Core detects a mismatch between:
- **Compiled Model**: Generated by `dotnet ef dbcontext optimize` (static snapshot)
- **Runtime Configuration**: Applied in `OnModelCreating()` via explicit `ApplyConfiguration()` calls

**Why This Happens**:
1. Compiled model was generated at a point in time
2. Entity configurations have been modified since (e.g., new indexes, column types)
3. `OnConfiguring()` calls `UseModel(ScriptsDbContextModel.Instance)` which locks the model
4. Runtime configuration changes are ignored because the compiled model takes precedence
5. Migration validation fails because it sees a mismatch

**Evidence**:
```csharp
protected override void OnConfiguring(DbContextOptionsBuilder optionsBuilder)
{
    base.OnConfiguring(optionsBuilder);
    optionsBuilder.UseModel(ScriptsDbContextModel.Instance);  // ← LOCKS MODEL
}

protected override void OnModelCreating(ModelBuilder mb)
{
    mb.ApplyConfiguration(new Configuration.ArtistConfiguration());
    // ... more configurations
    // These are IGNORED because UseModel() already locked the model
}
```

### Secondary Failure Pattern: Docker Container Crashes (20 failures)

**Error Message**:
```
Docker.DotNet.DockerApiException: Docker API responded with status code=Conflict, 
response={"message":"container ba95a3dc0f3d is not running"}
```

**Root Cause**: Testcontainers container crashes during test execution, likely due to:
1. **Resource exhaustion**: Multiple tests creating containers in parallel
2. **Timeout during migration**: `Database.MigrateAsync()` takes >80 seconds on some tests
3. **Container lifecycle**: Container stops before test completes
4. **Fixture reuse**: Each test creates a new fixture, but cleanup is incomplete

**Evidence**:
- Test logs show `pg_isready` checks every 1-2 seconds for 80+ seconds
- Container crashes after ~80 seconds of waiting
- Multiple containers created (ba95a3dc0f3d, a27fb0e2c698, 0b0e56b38578, b4c191c7d831)
- No cleanup between tests

## 5. Systematic Debugging Findings

### Chronic Failure Patterns

#### Pattern 1: Compiled Model Lock (53 failures)

**Symptom**: "Pending model changes" error during migration

**Root Cause**: `UseModel()` in `OnConfiguring()` prevents runtime configuration

**Prevention Strategy**:
1. Remove `UseModel()` call during test execution
2. Use compiled model only in production (via conditional logic)
3. Regenerate compiled model after any entity change
4. Add pre-test validation to ensure model sync

**Quick Win**: Disable compiled model in test DbContext

#### Pattern 2: Container Lifecycle (20 failures)

**Symptom**: Docker container crashes after 80+ seconds

**Root Cause**: 
- Migration takes too long (80+ seconds)
- Container timeout during readiness check
- Multiple containers created without cleanup

**Prevention Strategy**:
1. Increase container startup timeout
2. Implement proper fixture cleanup
3. Use shared container across tests (not per-test)
4. Add container health monitoring

**Quick Win**: Increase `WaitUntilAsync` timeout in Testcontainers

#### Pattern 3: Fixture Reuse (implicit)

**Symptom**: Each test creates new fixture, causing resource exhaustion

**Root Cause**: `DatabaseTestFixture` created per test method

**Prevention Strategy**:
1. Use TUnit's `[Before]` / `[After]` hooks for fixture lifecycle
2. Implement `IAsyncLifetime` pattern
3. Share container across test class
4. Implement proper disposal

**Quick Win**: Move fixture to class-level with proper async initialization
